# 11.1. Kafka Producer — Message Keys

This is an important producer concept because the **message key can influence which partition receives a record**, and therefore affects **ordering and distribution**.

---

# 1. What is a Message Key?

A Kafka record can contain:

```text
┌─────────────────────────┐
│ Kafka Record            │
│                         │
│ Key   → customer-101    │
│ Value → PAYMENT_DONE    │
└─────────────────────────┘
```

The key can be:

* String
* Number
* UUID
* Binary data
* Other serialized data

### Simple definition

> **A Kafka message key is an optional value attached to a record that the producer's partitioning logic can use to determine the target partition.**

Kafka's `ProducerRecord` is essentially a key/value record sent to a topic or partition. ([Apache Kafka][1])

---

# 2. Why Do We Need Message Keys?

The biggest reason:

> **To keep related records together in the same partition.**

Suppose:

```text
Topic: order-events

P0
P1
P2
```

We have:

```text
ORD-1001 CREATED
ORD-1001 PAID
ORD-1001 SHIPPED
```

Producer uses:

```text
Key = ORD-1001
```

Conceptually:

```text
ORD-1001
    ↓
Partitioner
    ↓
P1
```

Therefore:

```text
P1

Offset 10 → ORD-1001 CREATED
Offset 11 → ORD-1001 PAID
Offset 12 → ORD-1001 SHIPPED
```

Because these events are in the same partition, Kafka can maintain their **partition-level ordering**.

# 4. Key → Partitioner → Partition

This is the most important chain:

```text
Kafka Record
     │
     ├── Key
     │
     └── Value
          │
          ▼
      Partitioner
          │
          ▼
       Partition
```

Example:

```text
Key = ORD-1001
Value = ORDER_CREATED

        ↓

    Partitioner

        ↓

       P1
```

### Remember:

> **The key is NOT the partition.**

The key is an **input to the partitioning logic**.

---

# 5. What Happens When `key != null`?

This is the important case.

Suppose:

```text
Partitions = 3

Key = ORD-1001
```

Under Kafka's default partitioning logic, a record with a key is assigned based on a hash of the key. 

Conceptually:

```text
ORD-1001
    ↓
   Hash
    ↓
Partitioner
    ↓
   P1
```

Then another event:

```text
Key = ORD-1001
Value = PAYMENT_COMPLETED
```

is mapped consistently to that partition under the same partitioning configuration:

```text
ORD-1001
    ↓
   P1
```

So:

```text
P1

Offset 10 → CREATED
Offset 11 → PAYMENT_COMPLETED
Offset 12 → SHIPPED
Offset 13 → DELIVERED
```

---

# 6. 🔥 Why Does Same Key Matter?

You already learned:

> **Ordering is guaranteed within a partition, not across partitions.**

Now connect the two concepts:

```text
Same business key
       ↓
Same partition
       ↓
Same ordered log
       ↓
Ordering for those related events
```

Example:

```text
Key = ORD-1001

CREATED
PAID
SHIPPED
DELIVERED
```

can become:

```text
P1

Offset 10 → CREATED
Offset 11 → PAID
Offset 12 → SHIPPED
Offset 13 → DELIVERED
```

# 8. What If We Didn't Use a Key?

Imagine:

```text
DEPOSIT ₹10,000 → P0
WITHDRAW ₹2,000 → P3
TRANSFER ₹1,000 → P5
```

Now:

```text
P0 → DEPOSIT
P3 → WITHDRAW
P5 → TRANSFER
```

There is no single partition ordering across P0, P3 and P5.

Kafka cannot give you a global:

```text
DEPOSIT
   ↓
WITHDRAW
   ↓
TRANSFER
```

ordering across those independent partitions.

This is why choosing the correct key is important when ordering matters.

# 9. What Happens When `key = null`?

This is the part that needs to be **corrected from your original slide**.

### ❌ Don't memorize:

```text
key = null
↓
P0 → P1 → P2 → P0 → P1 → P2
```

That describes **round-robin partitioning**, but round-robin is not the modern default producer behavior.

### ✅ Current default behavior

When:

```text
No partition specified
+
Key = null
```

Kafka's default partitioning logic uses **sticky partitioning**.

It tends to stick to a partition while building a batch, then changes the partition when the batch reaches the relevant size. 

Conceptually:

```text
key = null
     ↓
Default partitioning
     ↓
Sticky partition
```

For example:

```text
P0:
Event 1
Event 2
Event 3
Event 4
     ↓
batch fills
     ↓
P2:
Event 5
Event 6
Event 7
     ↓
batch fills
     ↓
P1:
Event 8
Event 9
...
```

**Do not memorize the exact P0 → P2 → P1 sequence.**

The important concept is:

> **Without a key, modern Kafka's default partitioning can stick records to a partition for batching efficiency rather than strictly rotating P0 → P1 → P2.**

---

# 10. What Is Round Robin Then?

Kafka does provide a `RoundRobinPartitioner`.

If you explicitly configure it, records are distributed across partitions in round-robin fashion. Kafka's current API documentation describes it as distributing writes across partitions equally. ([Apache Kafka][2])

Then you can conceptually get:

```text
Event 1 → P0
Event 2 → P1
Event 3 → P2
Event 4 → P0
Event 5 → P1
Event 6 → P2
```

So:

```text
┌─────────────────────────────────┐
│ key = null                      │
├─────────────────────────────────┤
│ Default → Sticky partitioning   │
│ Explicit RoundRobin → RoundRobin│
└─────────────────────────────────┘
```

---

# 11. Same Key vs No Key

| Record                           | Partitioning behavior                  |
| -------------------------------- | -------------------------------------- |
| Key present                      | Default logic hashes key → partition   |
| Key null                         | Default logic uses sticky partitioning |
| Key null + RoundRobin configured | Round-robin distribution               |
| Explicit partition supplied      | That partition is used                 |

The current Kafka producer configuration documents all of these partitioning behaviors.

# 14. What If We Use `customerId` Instead?

Suppose:

```text
Customer = CUST-500

Order 1001
Order 1002
Order 1003
```

If:

```text
Key = CUST-500
```

then those events can be mapped to the same partition:

```text
CUST-500
    ↓
P2
```

So:

```text
P2

Order 1001
Order 1002
Order 1003
```

This is useful if your requirement is:

> **"Events for the same customer must remain ordered."**

But if you only require:

> **"Events for the same order must remain ordered."**

then:

```text
Key = orderId
```

may be more appropriate.

# 15. Key Selection Is a Design Decision

Always ask:

> **"For which business entity do I need ordering?"**

### Order-level ordering

### Customer-level ordering


### Account-level ordering

```text

```

### Truck-level ordering

```text

```

So:

```text
Business requirement
       ↓
Which entity needs ordering?
       ↓
Choose identifier
       ↓
Kafka key
       ↓
Partition
       ↓
Ordering
```

# 18. ⚠️ Hot Partition Problem

There is also a Platform Engineer consideration.

Suppose:

```text
Topic:
100 partitions
```

But one key produces massive traffic:

```text
Key = CUSTOMER-VERY-HIGH-VOLUME
```

That key may repeatedly map to one partition:

```text
P57

│
├── Event
├── Event
├── Event
├── Event
├── Event
└── millions of events
```

While:

```text
P0 → light
P1 → light
P2 → light
...
P56 → light
P58 → light
...
```

Now:

```text
P57 = HOT PARTITION 🔥
```

So there's a trade-off:

```text
Key
 ↓
Same partition
 ↓
Ordering ✅
 ↓
But potentially concentrated workload ⚠️
```

For now, just understand the trade-off. We don't need to jump into advanced hot-key mitigation yet.

# 22. 🎯 Interview Answer

### "What is a Kafka message key and why is it important?"

> **"A Kafka message key is an optional value associated with a record that the producer's partitioning logic can use to determine the target partition. With the default partitioning logic, a non-null key is hashed to select a partition. Using a stable business key such as `orderId` allows related events to be mapped to the same partition, giving ordering for those events. Different keys can be distributed across different partitions, enabling parallelism. Therefore, partition-key selection is an important design decision because it affects ordering, partition distribution and the possibility of hot partitions."**
